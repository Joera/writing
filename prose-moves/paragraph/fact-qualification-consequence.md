# Fact, qualification, consequence

## Use when
- A paragraph states a technical fact that has an important exception or limit, and a practical result.
- The three are currently tangled in one long sentence.

## Don't use when
- There is no qualification; don't invent one.

## Conflicts with
- [build-then-land](build-then-land.md) for the same paragraph: this is a three-step shape, not a build.

## Tags
`persuasion: mechanism`, `certainty: flat, with limits`

## Safe or adds
Safe.

## The move
Three beats, in order. The fact, stated flat. The qualification, stated flat, starting with a plain connective ("But", "Except"). The consequence, starting with "So" or a colon.

## Before
> The path to that content is the domain, and while browsers do not support distributed domains, it is prone to the risks of DNS, where the name can be seized, poisoned, or made hard to resolve. The protocol makes the name the publication's own, but it does not make it immune to the risks of the path it rides on.

## After
> The protocol makes the name the publication's own. But the path to that name still runs through DNS, because browsers do not yet resolve distributed domains, and on DNS a name can be seized, poisoned or made hard to resolve. So the name is owned, not immune.

## Pitfalls
- Qualification buried mid-sentence where readers miss it.
- A consequence that overstates.
