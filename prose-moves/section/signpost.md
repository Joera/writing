# Signpost

## Use when
- A run of parallel units (cases, scenarios, options) could be read as one continuous argument.
- The text later refers back to the set ("in all three cases"), so the reader needs to know it is a set.

## Don't use when
- The structure is already obvious from headings.
- The signpost would only announce what the next sentence says anyway.

## Conflicts with
- `presence: invisible` only if phrased in the first person ("we will now look at…"). An impersonal signpost is fine.
- Run-in labels on each unit in a document that should not read as a report.

## Tags
None.

## Safe or adds
Safe: it names a structure already there.

## The move
Put one plain sentence before the set that says what it is and why it's there, then get out of the way. Choose the quietest marker that works, in this order: one bridge sentence; then parallel openers ("Or…"); then run-in labels. Use one, not all three.

## Before
> Polyphony is a protocol, not a platform. [...]
>
> Two journalists work a beat together for years: [...]

## After
> Polyphony is a protocol, not a platform. [...]
>
> Three situations show the problem as writers and editors meet it today. Two journalists work a beat together for years: [...]

*(Chosen in the Polyphony introduction over "Or" openers and labels.)*

## Pitfalls
- "This" in the signpost pointing at the wrong thing when another paragraph sits in between ("the problem", not "this").
- Signposting every section, which reads as a table of contents.

## Combines with
[cases-first](../document/cases-first.md), [return-to-cases](../document/return-to-cases.md)
